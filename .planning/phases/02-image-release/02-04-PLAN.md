## 目标

把「先镜像、后版本号」从约定变成**依赖图强制**；把三个最容易悄悄写错的东西（tag 是否存在、manifest 是否真是双架构、workflow 结构与权限是否越界）变成**可单测的纯函数**，而不是写死在 `run: |` 里。

## 顺序如何被强制（含唯一例外通路）

```
workflow_dispatch(version, resume_from_verify=false)
  └─ guard   读 config.yaml → version/ref；校验格式；校验与 input 一致
             ├ 非 resume：断言该镜像 tag 在 GHCR 尚不存在（authenticated inspect）
             └ resume  ：断言该镜像 tag 在 GHCR 已存在（否则 resuming 无意义）
       └─ static   validate:workflows → validate:app → validate:dockerfile → lint → typecheck → test → check:app
            └─ publish   if: !resume_from_verify
                         check-tag-free（fail-closed）→ buildx 双架构 push（provenance/sbom 关闭）
                 └─ verify-image   if: always() && static 绿 && (publish 绿 || (resume && publish skipped))
                                   清 auths → 匿名 pull 成功 → assert-image.sh → manifest 平台/版本断言
                      └─ tag    needs: [guard, verify-image] → 只在此刻建 git tag（已指向 HEAD 则幂等通过）
```

`tag` 只有 `verify-image` 绿时才可能运行，而 `verify-image` 绿意味**在无凭据状态下能拉到该镜像** —— 比「带 token 能 inspect 到」更强，也正是 Supervisor 的真实路径。

## 为什么必须有 `resume_from_verify`（否则是死锁）

首次发布时 GHCR package 默认 private（研究 §4.5）。于是：`publish` 成功 → `verify-image` 的匿名 pull 失败 → `tag` 被跳过 → 人工改可见性 → **重跑**：

- 走完整流程：`check-tag-free` 因 tag 已存在而 fail-closed 拒绝 → 永远到不了 `verify-image`。
- 为让重跑通过而放宽 `check-tag-free`：直接破坏 T-02-05 的核心保证。

所以把「不重建、只复核」做成**显式可审计的 input**：`resume_from_verify: true` 时 `publish` 被 `if` 跳过，`verify-image` 用 `always()` 分支运行，`guard` 反向要求「镜像必须已存在」。run 记录里留着该 input，审计可查。

## Tasks

### Task 1 — tag 存在性判定（纯函数 + CLI）

- **read_first**: `02-RESEARCH.md` §4.3、`scripts/validate-app-metadata.mjs`（错误输出风格）
- **files**: `scripts/check-tag-free.mjs`、`scripts/check-tag-free.test.mjs`
- **action**:
  1. 导出纯函数 `classifyTagState({ exitCode, output })` → `"exists" | "free" | "auth-error" | "unknown-error"`。**判定顺序：先 auth 关键字、再 free 关键字**，避免 `unauthorized ... 404` 被误判为 free。`exitCode === 0` → `exists`；含 `manifest unknown`/`no such manifest`/`not found`/`404` → `free`；含 `unauthorized`/`denied`/`403`/`authentication required`/`insufficient_scope` → `auth-error`；其余 → `unknown-error`。
  2. 导出第二个纯函数 `classifyPackageState({ probes })` → `"absent" | "present" | "unknown"`，`probes` 是**两次** `gh api` 的结果：`/repos/<owner>/<repo>/packages/container/<pkg>` 与 `/users/<owner>/packages/container/<pkg>`。任一 exit 0 且输出含 `"id"` → `present`；**两处都** 404（`HTTP 404`/`Not Found`）→ `absent`；其余（含未认证导致的空输出）→ `unknown`。**只用于「包本身还不存在」这一种判断**，不得用它判断某个 tag 是否存在（研究 §4.3：versions 列表对缺失 tag 返回 200）。两处端点都查，是因为「私有但存在」在单一端点上也可能返回 404，只查一处会把「看不见」误判成「不存在」。
  3. CLI `node scripts/check-tag-free.mjs <image-ref> [--expect exists|free] [--allow-missing-package]`（默认 `free`）：真实调用 `docker manifest inspect`。期望与实际不符即 exit 1；`exists` 分支打印 `✗ tag already exists in GHCR; bump config.yaml version`。**`--allow-missing-package` 仅豁免一种情况**：分类为 `auth-error` 且 `classifyPackageState` 判 `absent` 时，打印 `::warning::package has never been published; treating tag as free` 并 exit 0；包存在（`present`）或状态为 `unknown` 时仍 exit 1。`unknown-error` 一律 exit 1，与 flag 无关。**`gh` 必须有凭据**（`GH_TOKEN`），否则两次 probe 都是 `unknown`，豁免不触发，安全地回落到 fail-closed。
  4. 为什么需要这一步：首次发布时 GHCR 包还不存在，`docker manifest inspect` 只能给出 `denied/unauthorized`，与真正的权限故障无法区分。若无此豁免，guard 的 `--expect free` 必然红，而 resume 又要求镜像已存在 —— 两条通路互斥，第一次发布永远发不出去。
  5. 测试用固定字符串喂两个纯函数，不依赖 Docker 与 gh CLI。
- **verify**:
  - `<automated>cd d:/workSpace/HomeWeave/homeweave; node --test scripts/check-tag-free.test.mjs; if ($LASTEXITCODE -ne 0) { exit 1 }; 'ok'</automated>`
- **acceptance**: 四类 tag 分类 + 三类包状态各有用例；`auth-error` 在**不带** flag 时 exit 1、**带** flag 且包 `absent` 时 exit 0、**带** flag 但包 `present` 时 exit 1；`unknown-error` 从不被 flag 放行。

### Task 3 — `scripts/validate-workflows.mjs`（结构化断言 + 红例）

- **read_first**: `02-RESEARCH.md` §4.1、§4.2、§4.6；`scripts/validate-app-metadata.mjs`
- **files**: `scripts/validate-workflows.mjs`、`scripts/validate-workflows.test.mjs`、`package.json`
- **action**:
  1. 新增三条 script：`"validate:workflows": "node scripts/validate-workflows.mjs --profile all"`、`"validate:workflows:ci"`、`"validate:workflows:release"`。后两条供 Task 4/5 使用（彼时另一个文件尚不存在）。
  2. **解析后按对象/布尔取值断言，禁止 `JSON.stringify` 子串匹配**。导出下列纯函数，每个返回 `problems: string[]`：
     - `checkFiles(profile, cwd)`：`ci` 要 `ci.yml`，`release` 要 `release.yml`，`all` 要两者。**任一缺失 → problem**（`✗ missing workflow file: <path>`）。
     - `checkNoPrivilegedPrTrigger(doc)`：`on` 不得含 `pull_request_target`；`on: push` 简写要归一。
     - `checkPermissions(doc, allow)`：顶层 `permissions` 必须存在且**恰为** `{contents:'read'}`（多余键即 problem）；`packages: write` 只允许出现在 `allow.packagesWrite` 列的 job 且该 job 必须真有；`contents: write` 同理。
     - `checkPinnedActions(doc)`：每个 `steps[].uses` 匹配 `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+@v\d+(\.\d+\.\d+)?$`。
     - `checkJobGraph(doc, edges)`：`needs` 为字符串时归一为数组，逐条断言包含。**必须写死的边集**：
       - `ci`：`static` 无上游（单 job）。
       - `release`：`static ⊇ [guard]`、`publish ⊇ [static]`、`verify-image ⊇ [publish, static]`、`tag ⊇ [guard, verify-image]`。
       - 反向断言：`publish` **不得**出现在 `verify-image` 之外任何 job 的 `needs` 里（防止有人把 tag 挂到 publish 上）。
     - `checkBuildPushFlags(doc, job)`：**先要求该 job 内必须存在** `uses` 以 `docker/build-push-action@` 开头的 step，**找不到即 problem**（否则改用 `run: docker buildx build --push` 就能绕过 D-5 的全部布尔契约）。找到后**结构化断言** `with.push === true`、`with.provenance === false`、`with.sbom === false`（布尔，不是字符串 `'true'`/`'false'`）、`with.platforms` 切分排序后 `=== ['linux/amd64','linux/arm64']`、`with.context === '.'`、`with.file === './Dockerfile'`；`with.tags` 必须含 `type=raw,value=`，不含 `type=semver`/`latest`/`type=sha`。
     - `checkNoShellBuild(doc, job)`：该 job 所有 `run` 不得含 `docker build`、`docker buildx build`、`--push`（构建只能经由 build-push action，凭证与 provenance 语义才可审计）。
     - `checkStepRuns(doc, job, snippets)`：**取值面 = 该 job 所有 step 的 `run` 文本 + 所有 step 的 `env` 键与值**（拼接成一个字符串再断言），因为 `GH_TOKEN` 这类前提写在 `env:` 而不是 `run:` 里；只扫 `run` 会让 env 断言永远不可满足。逐条断言包含。**必须覆盖**：`guard` ⊇ {`check-tag-free.mjs`, `--expect free`, `--expect exists`, `--allow-missing-package`, `GH_TOKEN`}（**两个分支都要断言**，否则可把它写成单分支而全绿）；`publish` ⊇ {`check-tag-free.mjs`, `--allow-missing-package`, `GH_TOKEN`}；`verify-image` ⊇ {`assert-image.sh`, `assert-manifest-platforms.mjs`, `docker logout`, `.docker/config.json`, `docker pull`}；`tag` ⊇ {`git config user.email`, `git tag`, `git push`}（只建本地 tag 不推送就等于没交付）。
     - `checkCiGates(doc)`：全部 `run` 拼接后含 `validate:workflows`、`validate:app`、`validate:dockerfile`、`lint`、`typecheck`、`test`、`check:app` 七个 token；且不含 `build-push-action`、`docker build`。
     - `checkDispatch(doc)`：`on` 键恰为 `['workflow_dispatch']`；`inputs.version.required === true`；`inputs.resume_from_verify.type === 'boolean'` 且 `default === false`。
     - `checkResumePath(doc)`：`publish.if` 必须含 `!inputs.resume_from_verify`；`verify-image.if` 必须**同时**含 `always()`、`needs.publish.result == 'skipped'`、`needs.static.result == 'success'`，且**不得**出现 `!= 'skipped'`（否则条件被反转后仍能通过词面检查）；`verify-image.needs` 含 `publish` 与 `static`。
     - `checkJobsHaveCheckout(doc)`：`release` 的每个 job（`guard`/`static`/`publish`/`verify-image`/`tag`）首个 step 必须是 `actions/checkout@v7`；**`tag` 的 checkout 还必须 `with['fetch-depth'] === 0`**（默认浅取不拉 tag，远端已存在的同名 tag 本地查不到，幂等判断失效）。缺 checkout 会让 `context: '.'` 变成空目录、`scripts/ci/assert-image.sh` 与 `apps/api/prisma/ENGINE_DECISION` 都不存在。
  3. CLI 汇总打印 `✓ workflow checks passed (<n> rules)`；任一 problem 打印 `✗ <rule>: <detail>` 并 `process.exitCode = 1`。

## 已知风险

- 首次真实发布前，`publish`/`verify-image` 的实际行为无法本地验证。**首次 run 必须有人值守**，并如实记录哪些断言真的执行过。
- **第一次 run 预期会在 `verify-image` 的匿名 pull 处变红**（package 默认 private）。这是设计意图而非缺陷；按手册 §4 走 resume。
- `gitleaks` 未纳入本计划 job 清单。SEC-03 由 `docker history --no-trunc` 断言、镜像文件系统扫描与 `.dockerignore` 覆盖；**git 历史中的密钥不在覆盖范围内**（已在手册 §7 明写）。若要加独立扫描 job，需先确认 action 的 license 要求（研究 A4），不宜在无验证的情况下写入 workflow。
- `docker manifest inspect`/`docker pull` 对 GHCR 的实际 stderr 文案未经本机验证（无 Docker）；若首次 CI 显示文案与 `classifyTagState` 的关键字不匹配，按「unknown-error → fail-closed」处理并补关键字，**不得放宽为「非零即空闲」**。特别要观察**第二次**发布（包已存在、viewer 用 `packages: write` token）时远端对「缺失 tag」返回的文案：若返回 denied 而非 manifest unknown，第二次发布仍会卡在 guard，此时需要靠实测文案补一档判据，而不是靠豁免。
- 「私有但存在」的包原则上会被两处端点都 404 到 → 被误判 `absent` → 豁免放行，进而可能覆盖同名 tag。缓解：`GITHUB_TOKEN` 带 `packages: write` 时对自有包可见，正常不会落到这条路径；且一旦发生覆盖，run 日志里会有 `::warning::package has never been published`，可事后审计。**这是本阶段接受的残余风险，不隐藏。**
