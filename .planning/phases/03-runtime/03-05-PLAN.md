# 03-05 — 启动 fail-fast、优雅关闭与镜像断言 8→9

## 目标

配置错时**不服务**，被要求停止时**干净地停**，并让镜像自己能证明这两件事。

## 边界（明确不做）

不改 `/health/live` 响应体（SC-1）、不改 ready 三项检查语义（03-04）、不改生成器（03-02）。

## Tasks

### Task 1 — 启动四步校验与退出码

- **read_first**: `03-RESEARCH.md §8.1/§8.2`、`apps/api/src/config/app-config.ts`（03-01 产物）、`apps/api/src/prisma/prisma.service.ts`、`AGENTS.md`（不得带着半可用状态服务）
- **files**: `apps/api/src/lifecycle/startup-checks.ts`、`apps/api/src/config/errors.ts`、`apps/api/src/main.ts`
- **action**:
  1. `errors.ts`：`ConfigError extends Error` 带 `exitCode = 78`；`StartupError extends Error` 带 `exitCode = 1`。
  2. `runStartupChecks({ prisma, config, logger })` 按序短路：
     - 配置：`port` 为整数且在 1..65535，`databasePath` 非空 → 失败 `ConfigError`
     - 目录：`fs.accessSync(dirname(databasePath), W_OK)` → 失败 `ConfigError('dir_readonly'|'dir_missing')`
     - 写测试（**仅此一次**）：在数据目录建 `.hw-write-probe` 后立即删除 → 失败 `ConfigError('write_failed')`
     - 磁盘余量：`checkDisk()`；`low` 只警告不阻断（余量不足时重启也不会变好）
     - 真实查询：`select 1` → 失败 `StartupError('query_failed')`
  3. `main.ts`：`loadAppConfig()` → `NestFactory.create(..., { bufferLogs: true })` → `useLogger` → `await runStartupChecks()` → `listen()`。整段 `try/catch`，`catch` 内打印**一条** `event:'startup_failed'`（含 `reason`、`exitCode`）后 `process.exit(exitCode)`。
  4. 成功后打印一行 `startup_ok`，含 `port`、`databasePath`、`logLevel`、`migrations` 诊断值；`migrations === 'unknown'` 时降为 `warn`。
  5. **`listen` 必须在校验之后**，避免「端口已开但 DB 不可用」窗口。

### Task 2 — 优雅关闭

- **read_first**: `03-RESEARCH.md §7.1/§7.2/§7.3`（Nest 12 源码行为）、`apps/api/src/lifecycle/shutdown-state.ts`
- **files**: `apps/api/src/lifecycle/shutdown.service.ts`、`apps/api/src/main.ts`、`apps/api/src/prisma/prisma.service.ts`
- **action**:
  1. `shutdown.service.ts`：实现 `BeforeApplicationShutdown` —— 置 `shuttingDown = true`，记起始时间，log `msg:'shutdown: stop accepting new requests'`。**不要**手动 `server.close()`（Nest 会做）。
  2. `main.ts`：`app.enableShutdownHooks(Object.values(ShutdownSignal), { useProcessExit: true })`。**必须**带 options：默认分支是 `process.kill(pid, signal)` 重放信号（exit 143），且源码注释明确异步 logger 缓冲需 `process.exit(0)` 才刷干净。
  3. 8s 兜底：`shutdown_begin` 时启动 `setTimeout(...).unref()`，到期 log `shutdown_forced` 后 `process.exit(0)`（自愿退出，仍满足「无 SIGKILL」）。
  4. `PrismaService.onModuleDestroy` 内 `$disconnect()` 并 log `msg:'shutdown: prisma disconnected'`。
  5. 日志顺序契约：`stop accepting new requests` → `prisma disconnected` → 退出。

## 残余风险（必须在真机确认，不要静默通过）

**`USER node` 与 `/data` 权限（RESEARCH A2，本阶段最大未知）。** Dockerfile 以 `node` 用户运行，而 HA Supervisor 挂载的 `/data` 通常属 root。若不可写，本计划设计的 fail-fast 会在**真实部署里第一次启动就退出 78** —— 本地（Windows、可写目录）全绿。

处置顺序：
1. 真机启动一次，看是否 78 + `dir_readonly`
2. 若是：优先让 Dockerfile 在 entrypoint 里修正 `/data` 权限（仅当以 root 启动时），或在 `config.yaml` 中声明所需权限
3. **不要**未经验证就把 `USER node` 改回 root —— 那会失去 Phase 2 建立的非 root 运行保证

此风险不阻断本计划完成，但必须在 SUMMARY 落一条 open question，并建议在 Phase 4 之前解决。
